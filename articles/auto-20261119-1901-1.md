AIコーディングエージェントが日常の開発に入り込み、ツール選びの基準も変わりつつあります。以前は「エディタが使いやすいか」「実行速度が速いか」が中心でしたが、現在は**AIから扱いやすいか**、**ローカルで完結できるか**、**設定をチームで共有しやすいか**といった観点も重要です。

本記事では、ここ1〜2年で開発現場への導入が進んでいるツールと規格を7つ取り上げ、実務での使いどころと注意点を整理します。

## 開発ツール選びで見るべき3つの軸

最初に、筆者がツールを選ぶ際に重視している観点を整理します。

- **AIエージェントとの相性**：CLIや設定ファイルが機械可読で、エージェントから操作しやすいか
- **再現性**：ローカルとCIで同じ環境を再現できるか
- **設定の一元化**：複数ツールの設定が散らばらず、レビューしやすいか

すべてを満たすツールは多くありませんが、この3軸で見ると導入後の運用コストを判断しやすくなります。

## 1. MCP（Model Context Protocol）— AIと開発ツールをつなぐ共通規格

MCPは、AIアプリケーションと外部ツール・データソースを接続するためのオープンなプロトコルです。ファイルシステム、Git、データベース、社内APIなどをAIエージェントから利用するための共通インターフェースとして注目されています。

従来はツールごとに独自の連携コードを書く必要がありましたが、MCPに対応したサーバーを用意すれば、対応クライアントから共通の方法で呼び出せます。

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./"]
    }
  }
}
```

設定ファイルの場所や書式はクライアントによって異なります。また、MCPサーバーはローカルのファイルや認証情報へアクセスできるため、**許可するディレクトリと権限を最小限にする**ことが重要です。便利さと引き換えに、サプライチェーンと権限管理のリスクを必ず確認しましょう。

## 2. uv — Pythonの環境構築を高速化する

uvはAstralが開発するPythonのパッケージ・プロジェクト管理ツールです。依存解決とインストールが高速で、ロックファイルによる再現性のある環境構築ができます。

```bash
uv init my-app
cd my-app
uv add requests
uv run python main.py
```

`uv run`を使うと、プロジェクトの仮想環境を意識せずにコマンドを実行できます。Python本体のバージョン管理もできるため、ローカルとCIの差分を減らしやすいのが利点です。

既存プロジェクトへ導入する場合は、`pyproject.toml`とロックファイルの扱いをチームで決めてから移行すると混乱を避けられます。

## 3. Biome — LintとFormatを1か所にまとめる

BiomeはRust製のリンタ・フォーマッタです。JavaScript/TypeScriptやJSONを中心に、LintとFormatを高速に実行できます。

```bash
npm install --save-dev --save-exact @biomejs/biome
npx biome init
npx biome check --write .
```

ESLintとPrettierを別々に設定しているプロジェクトでは、設定ファイルを1つに寄せられるのが魅力です。エディタの保存時整形とCIのチェックを同じ設定で運用できるため、「ローカルでは通るがCIで落ちる」といった差異も減らせます。

移行時は一度にすべてのルールを有効にせず、まずはFormatterとして導入し、その後Lintルールを段階的に追加するのが安全です。

## 4. Bun — 実行・テスト・パッケージ管理を統合する

BunはJavaScript/TypeScript向けのオールインワンランタイムです。パッケージマネージャ、バンドラ、テストランナーが一体になっており、小さなプロジェクトほど初期設定の手間を減らせます。

```bash
bun init
bun add -d typescript
bun test
```

TypeScriptをそのまま実行できるため、スクリプトやCLIツールの作成が快適です。Node.jsとの互換性は向上していますが、ネイティブモジュールや一部APIの挙動は異なる場合があります。本番導入前に対象プロジェクトで検証しましょう。

## 5. Zed — 軽快さとAI連携を両立するエディタ

ZedはRust製のコードエディタです。起動や入力のレスポンスが軽く、LSPやTree-sitterによる補完・構文解析を備えています。共同編集機能もあり、ペアプログラミングやレビューで活用できます。

VS Codeと比べると拡張機能の数は限られるため、利用する言語やフレームワークの対応状況は事前に確認が必要です。一方で、エディタ自体の軽さを重視する人や、AIとのインライン連携を試したい人には有力な選択肢になります。

## 6. Ollama — ローカルでLLMを動かす

Ollamaは、ローカル環境で大規模言語モデルを実行するためのツールです。CLIからモデルを取得してすぐに試せる手軽さが特徴です。

```bash
ollama pull qwen2.5-coder
ollama run qwen2.5-coder
```

コードや文章を外部サービスへ送りたくない場面に向いています。OpenAI互換のAPIを備えているため、既存のツールから接続しやすいのも利点です。

ただし、モデルのサイズによっては相応のメモリとGPU性能が必要です。また、ローカルモデルはクラウドモデルと比べて品質やコンテキスト長が劣る場合があるため、用途を限定して使うのが現実的です。

## 7. Dev Containers — 開発環境の差分をなくす

Dev Containersは、コンテナ内で開発環境を定義する仕組みです。エディタやCIで同じイメージを使えるため、「自分の環境では動く」という問題を減らせます。

```json
{
  "name": "my-app",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:22",
  "postCreateCommand": "npm install"
}
```

AIエージェントにコマンドを実行させる場合も、コンテナ内に閉じ込めることでホスト環境への影響を抑えられます。ただし、ファイルのマウントや認証情報の受け渡しには注意が必要です。秘密情報はイメージに含めず、実行時に注入するようにしましょう。

## 実務での組み合わせ方

一例として、次のような構成が考えられます。

| 用途 | ツール |
| --- | --- |
| AIと外部ツールの接続 | MCP |
| Pythonの依存管理 | uv |
| JS/TSのLint・Format | Biome |
| JS/TSの実行・テスト | Bun |
| エディタ | Zed |
| ローカルLLM | Ollama |
| 環境の再現 | Dev Containers |

すべてを一度に導入する必要はありません。まずは1つだけ試し、効果を確認してから広げると定着しやすくなります。特にMCPとローカルLLMは権限管理の設計が重要なので、小規模なリポジトリで検証するのがおすすめです。

## 導入時の注意点

- ロックファイルは必ずリポジトリへコミットする
- ローカルとCIで同じツールバージョンを使う
- MCPサーバーやエージェントに与える権限を最小限にする
- ライセンスとセキュリティポリシーを確認する
- 設定ファイルの管理責任者を決める

## まとめ

AIコーディング時代のツール選びでは、単なる機能の多さよりも、**AIから安全に扱えるか**、**環境を再現できるか**が重要になります。

今回紹介した7つは、いずれも小さく試せて効果を実感しやすいものです。気になるものがあれば、まずは手元のプロジェクトで1つだけ導入し、チームのワークフローに合うか確認してみてください。
