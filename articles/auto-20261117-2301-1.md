## はじめに：ツール選定の前提が変わった

ここ数年で、開発ツールの勢力図は大きく変わりました。背景にあるのは次の3つです。

- **Rust製ツールの台頭**：速度と配布のしやすさを武器に、従来の定番ツールを置き換えつつあります。
- **AIコーディングエージェントの普及**：人間だけでなくエージェントも読み書きする前提の設定・整形・静的解析が重要になりました。
- **モノレポとエディタ統合**：個別ツールより「一式で高速に動く」ことが評価されるようになりました。

この記事では、2026年時点で実務的に存在感のあるツールを、Python・JavaScript/TypeScript・エディタの3カテゴリで整理します。特定のニュースを断定的に紹介するのではなく、「今どんな基準で選ぶと失敗しにくいか」に焦点を当てます。


## Python：uv と Ruff を中心に据える

### uv：パッケージ管理と仮想環境を一本化

`uv` は pip / pip-tools / virtualenv / pyenv の役割をまとめて担う高速ツールです。Rust製で、依存解決とインストールが非常に速いのが特徴です。

```bash
uv init myapp
cd myapp
uv add fastapi uvicorn
uv run uvicorn main:app --reload
```

従来の `requirements.txt` 運用から移行する場合も、ロックファイルを生成して再現性を確保できます。

```bash
uv lock
uv sync
```

実務で効くのは、CIでの再現性です。`uv sync --frozen` を使えばロックファイル通りに環境を構築できるため、「ローカルでは動くのにCIで落ちる」問題を減らせます。

### Ruff：lint と format を1つに

`Ruff` はFlake8・isort・pyupgrade などの役割を統合したlinter兼formatterです。設定は `pyproject.toml` に集約できます。

```toml
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
```

```bash
ruff check --fix .
ruff format .
```

ポイントは、**lintとformatを同じツールに寄せる**ことです。設定ファイルが散らばらず、エディタ・pre-commit・CIで同じ結果が得られます。

### 型チェックはどうするか

`mypy` は引き続き有力ですが、`pyright` や `basedpyright` を選ぶチームも増えています。エディタの補完体験と揃えたいなら pyright 系、既存資産とプラグイン重視なら mypy、というのが現実的な判断基準です。

### Pythonツールチェーンの推奨構成

| 役割 | 選択肢 | 補足 |
| --- | --- | --- |
| パッケージ管理 | uv | ロックファイルで再現性確保 |
| lint / format | Ruff | 設定を `pyproject.toml` に集約 |
| 型チェック | pyright / mypy | エディタとの相性で選ぶ |
| テスト | pytest | 定番。並列化は pytest-xdist |

## JavaScript / TypeScript：Biome と Bun の現在地

### Biome：lint と format の統合

`Biome` は ESLint + Prettier の代替を狙うツールです。Rust製で高速、設定がシンプルという利点があります。

```bash
bun add -d @biomejs/biome
bunx biome init
bunx biome check --write .
```

ただし、ESLintの豊富なプラグインエコシステムに依存しているプロジェクトでは、移行コストが高い場合があります。**新規プロジェクトはBiome、既存の大規模プロジェクトは段階移行**が無難です。

### Bun：ランタイム兼パッケージマネージャ

`Bun` はJavaScriptランタイムであり、パッケージマネージャでもあります。テストランナーやバンドラも内蔵しており、「とりあえず一式揃う」体験が強みです。

```bash
bun install
bun run dev
bun test
```

本番ランタイムとして採用するかは、Node.jsとの互換性やエコシステムの成熟度を見て判断するのが安全です。開発体験目的で使い、本番はNode.jsという構成も十分あり得ます。

### 選定の考え方

- **既存プロジェクト**：ESLint + Prettierを維持しつつ、Biomeを段階的に試す。
- **新規プロジェクト**：Biome + Bunで開始し、必要ならNode.jsへ寄せる。
- **ライブラリ公開**：互換性重視でNode.js + 実績あるツールを選ぶ。

## エディタとAI支援：Zed・VS Code・エージェント連携

### エディタは「AIとの相性」で選ぶ時代

エディタ選びの基準に、AI補完やエージェント連携のしやすさが加わりました。`Zed` はRust製で高速、共同編集やAI機能を統合しています。`VS Code` は拡張機能の豊富さとエージェント系拡張の対応が強みです。

実務では「チーム全員が同じ編集体験を得られるか」が重要です。設定をリポジトリにコミットし、`.editorconfig` やフォーマッタ設定を共有しておくと、エディタが違っても差分が暴れません。

### エージェントに渡す前提の整備

AIコーディングエージェントが当たり前になると、次の整備が効きます。

1. **タスクランナーを明示する**：`make test` や `pnpm test` など、エージェントが実行すべきコマンドをREADMEに書く。
2. **lint/formatを自動化する**：エージェントの出力を機械的に整える。
3. **型とテストで境界を守る**：レビュー負荷を下げる。

```json
{
  "scripts": {
    "lint": "biome check .",
    "format": "biome format --write .",
    "test": "bun test"
  }
}
```

設定ファイルとコマンドが揃っているだけで、エージェントの試行錯誤のコストは大きく下がります。

## まとめ：2026年の現実的な構成

最後に、カテゴリ別の「無難な出発点」をまとめます。

- **Python**：uv + Ruff + pytest。型はpyrightかmypyを1つに絞る。
- **JS/TS**：新規はBiome + Bun、既存は段階移行。本番は互換性を確認。
- **エディタ**：ZedかVS Code。設定はリポジトリで共有。
- **AI連携**：コマンド・lint・型・テストを整備し、エージェントが迷わない環境にする。

ツールは目的ではなく手段です。「速い」「設定が少ない」「チームで揃えやすい」という3点で選ぶと、流行に振り回されにくくなります。まずは1カテゴリだけでも置き換えて、効果を測ってから広げるのがおすすめです。
