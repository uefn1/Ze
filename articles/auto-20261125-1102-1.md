## はじめに

複数の言語を扱うリポジトリでは、Node.jsはnvm、Pythonはpyenv、Goはgoenv……とバージョン管理ツールが乱立しがちです。さらにタスク実行はMakefile、環境変数はdirenv、と管理対象が増えるほど「このプロジェクトは何をどう揃えれば動くのか」が分かりにくくなります。

本記事では、こうした開発環境まわりの責務を1つにまとめられるツール **mise** を紹介します。バージョン管理・タスクランナー・環境変数管理をひとつの設定ファイルに集約でき、多言語リポジトリほど効果を発揮します。


## miseとは

mise（ミーズ）は、Rust製の開発ツール管理ツールです。もともとはasdfの高速な代替として知られていましたが、現在は次の3つの役割を担います。

- **ツールのバージョン管理**：Node.js、Python、Go、Rubyなどをプロジェクト単位で固定
- **タスクランナー**：Makefileやnpm scriptsの一部を置き換え
- **環境変数・PATH管理**：dotenvの読み込みやPATH追加を設定ファイルに集約

主な特徴は以下のとおりです。

- Rust製で起動・切り替えが高速
- asdfのプラグインエコシステムと高い互換性
- 既存の `.tool-versions` をそのまま読める
- `mise.toml` に設定を集約でき、チームで共有しやすい

## インストール

macOSならHomebrew、LinuxやmacOSならインストールスクリプトが使えます。

```bash
# macOS
brew install mise

# Linux / macOS
curl https://mise.run | sh
```

シェルにフックを追加して有効化します。以下はzshの例です。

```bash
echo 'eval "$(mise activate zsh)"' >> ~/.zshrc
exec zsh
```

bashなら `mise activate bash`、fishなら `mise activate fish` を指定します。インストール後は動作確認をしておきましょう。

```bash
mise --version
mise doctor
```

`mise doctor` は設定ファイルやシェル連携の状態を診断してくれるので、うまく動かないときの切り分けに便利です。

## グローバルにツールを導入する

まずはマシン全体で使うバージョンを決めます。

```bash
mise use --global node@lts
mise use --global python@3.12
node -v
python --version
```

`--global` を付けるとホームディレクトリ側の設定に書き込まれます。導入済みのツールは `mise ls` で一覧できます。

```bash
mise ls
```

## プロジェクト単位でバージョンを固定する

プロジェクトのディレクトリで `mise use` を実行すると、カレントディレクトリに `mise.toml` が生成されます。

```bash
cd my-app
mise use node@22 python@3.12
```

生成される `mise.toml` は次のようになります。

```toml
[tools]
node = "22"
python = "3.12"
```

このファイルをリポジトリにコミットすれば、チーム全員が同じバージョンを使えます。clone直後は次のコマンドで一括インストールできます。

```bash
mise install
```

バージョン指定は柔軟で、`22`（メジャー指定）、`22.11`（マイナー指定）、`lts`、`latest` などが使えます。再現性を重視するなら、実運用ではパッチまで固定するか、後述するロックの仕組みを併用するとよいでしょう。

なお、miseはasdfの `.tool-versions` も読み込めるため、既存プロジェクトをすぐに書き換える必要はありません。移行は段階的に進められます。

## タスクランナーとして使う

miseはタスクランナーとしても使えます。`mise.toml` にタスクを定義してみます。

```toml
[tasks.setup]
description = "依存関係のインストール"
run = "npm ci"

[tasks.dev]
description = "開発サーバーを起動"
run = "npm run dev"

[tasks.lint]
run = "npm run lint"

[tasks.test]
run = "npm test"

[tasks.ci]
depends = ["lint", "test"]
```

実行は `mise run` です。依存タスクは自動で解決されます。

```bash
mise run ci
mise r ci        # runの短縮形
mise tasks       # タスク一覧と説明を表示
```

`description` を付けておくと `mise tasks` で一覧性が上がります。`alias` を定義すれば、よく使うタスクに短い名前を付けられます。

Makefileやnpm scriptsをすべて置き換える必要はありません。言語をまたぐタスクや、複数コマンドをまとめたい処理だけmiseに寄せると、設定の見通しが良くなります。ただしチームによってはMakefileに慣れている場合もあるため、導入時は学習コストも含めて相談するとよいです。

## 環境変数とPATHをまとめて管理する

`[env]` セクションを使うと、環境変数やPATHをプロジェクト設定に集約できます。

```toml
[env]
NODE_ENV = "development"
_.file = ".env"
_.path = ["./node_modules/.bin"]
```

`_.file` はdotenvファイルの読み込み、`_.path` はPATHへの追加です。これまでdirenvなどで個別に管理していた設定を、`mise.toml` に寄せられます。反映内容は次のコマンドで確認できます。

```bash
mise env
```

## よく使うコマンド

日常的に使うコマンドをまとめておきます。

```bash
mise ls                 # 導入済みツールの一覧
mise ls-remote node     # インストール可能なバージョン一覧
mise outdated           # 更新可能なツールの確認
mise upgrade            # ツールの更新
mise exec -- node -v    # 設定を適用した状態でコマンド実行
mise doctor             # 環境の診断
```

`mise exec`（短縮形は `mise x`）は、シェルフックを有効にしていないCI環境などで特に役立ちます。

## asdfからの移行

asdfをすでに使っている場合、移行のハードルは比較的低めです。

- `.tool-versions` をそのまま読み込める
- 多くのasdfプラグインを利用できる
- 設定ファイルを `mise.toml` に置き換えていけばよい

まずはグローバル設定だけmiseに切り替え、プロジェクトごとの設定は動作を確認しながら徐々に移す、という進め方が安全です。

## 運用のコツと注意点

チームで導入する際に意識しておきたい点を挙げます。

- **共有設定と個人設定を分ける**：`mise.toml` はコミットし、個人固有の設定は `mise.local.toml` に置いてgitignoreする
- **初回の信頼確認**：設定ファイルによっては `mise trust` による信頼確認を求められることがある
- **CIでの扱い**：`mise install` の後に `mise exec -- <command>` で実行するか、シェルフックを有効化する
- **バージョン指定の方針**：緩めの指定は更新に強い一方で再現性が下がる。ロックの仕組みも整備されつつあるため、チームの方針に合わせて使い分ける
- **Windows**：ネイティブ対応も進んでいるが、チームによってはWSL前提のほうがトラブルが少ない

## まとめ

miseは「バージョン管理」「タスク実行」「環境変数管理」を1つの設定ファイルに統合できるツールです。多言語を扱うリポジトリや、開発環境のセットアップ手順が属人化しているチームほど導入効果が大きいと感じます。

まずは `mise use --global` でグローバル導入から始め、慣れてきたらプロジェクト単位の `mise.toml` とタスク定義に広げていくのがおすすめです。既存のasdfやMakefileをすぐ捨てる必要はないので、置き換えやすい部分から少しずつ試してみてください。
