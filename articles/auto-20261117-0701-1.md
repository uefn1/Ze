## はじめに

ここ数年、開発ツールの世界でひとつの大きな流れが続いています。それは「Rust（やZig）で書き直された高速なツール」が、これまで当たり前だった選択肢を置き換えつつあるという流れです。

Pythonのパッケージ管理、JavaScriptのリンター/フォーマッタ、エディタ、バンドラ。長年Node.jsやPython自身で書かれていた領域に、ネイティブバイナリのツールが次々と投入されています。

この記事では、そうしたツールの中でも特に「導入すると開発体験がはっきり変わる」ものを整理して紹介します。特定のバージョンや最新リリースの話ではなく、考え方と使い方の入り口をまとめることを目的としています。

## なぜRust製ツールが増えているのか

理由はシンプルです。

- **起動が速い**: インタプリタの初期化を待たずに実行できる
- **並列処理が得意**: ファイル走査やlintをコア数に応じてスケールさせやすい
- **配布が楽**: 単一バイナリで動くため、依存関係の衝突が起きにくい
- **メモリ安全**: 大規模なコードベースでも安定して動かしやすい

特に「ファイルを大量に読む」「繰り返し実行する」タイプの処理（フォーマット、lint、型検査、テスト）と相性が良く、CIの時間短縮にも直結します。

## uv — Pythonのパッケージ管理を一変させる

Pythonの依存管理は長らく `pip` / `virtualenv` / `poetry` / `conda` などが混在し、プロジェクトごとに作法が違うのが悩みでした。そこに登場したのが [uv](https://github.com/astral-sh/uv) です。

uvはRust製のパッケージ・プロジェクトマネージャで、pipの代替として使えるだけでなく、仮想環境の作成、依存のロック、Python本体のバージョン管理まで一通りこなします。

```bash
# プロジェクト作成
uv init myapp
cd myapp

# 依存追加（ロックファイルも更新される）
uv add requests

# 仮想環境を意識せずに実行
uv run python main.py
```

従来の `pip install` + `python -m venv` の手順を意識しなくてよくなるのが大きな変化です。`uv.lock` によって再現性も確保でき、CIでのセットアップも短くなります。

Pythonを書く人なら、まず試す価値が最も高いツールのひとつです。

## Ruff — lintとformatを1つに

同じくAstral製の [Ruff](https://github.com/astral-sh/ruff) は、Pythonのリンター兼フォーマッタです。Flake8、isort、pyupgrade、flake8-bugbear など、これまで複数ツールを組み合わせていた役割をひとつにまとめます。

```bash
ruff check .
ruff format .
```

設定は `pyproject.toml` にまとめられます。

```toml
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]
```

速度が速いので「保存のたびにlintを回す」という運用が現実的になります。エディタの保存フックと組み合わせると、指摘のほとんどをコーディング中に潰せます。

## Biome — JS/TSのフォーマットとlintを統合

JavaScript/TypeScript界隈では、PrettierとESLintの組み合わせが長年の定番でした。しかし設定が分散しがちで、ESLintのプラグイン解決に時間がかかるといった課題もありました。

[Biome](https://biomejs.dev/) は、フォーマッタとリンターをひとつのRust製ツールに統合したものです。

```bash
biome check .
biome format --write .
```

`biome.json` で設定を一元管理できます。

```json
{
  "formatter": {
    "indentStyle": "space",
    "indentWidth": 2
  },
  "linter": {
    "enabled": true
  }
}
```

既存のPrettier/ESLint構成をすべて置き換えられるわけではありませんが、新規プロジェクトや小〜中規模のリポジトリでは、ツールチェーンを大幅に簡略化できます。

## Bun — ランタイムとツールチェーンをまとめる

[Bun](https://bun.sh/) はJavaScriptランタイムでありながら、パッケージマネージャ、テストランナー、バンドラを内蔵しています。

```bash
bun install
bun run dev
bun test
```

複数のツールを別々に入れなくて済むため、立ち上げが速いのが魅力です。Node.jsとの互換性も意識されており、既存プロジェクトの一部だけBunに置き換える、といった試し方もできます。

## oxc / Rolldown / Turbopack — ビルド周りのネイティブ化

ビルドツールの領域でもネイティブ化が進んでいます。

- **oxc**: Rust製のJavaScriptパーサ/リンタ。高速な解析基盤
- **Rolldown**: Rust製バンドラ。Rollup互換APIを目指す
- **Turbopack**: Next.jsで使われるRust製バンドラ

いずれも「開発サーバの起動」「HMR」「本番ビルド」の待ち時間を縮める方向に寄与します。フレームワーク側が採用している場合は、設定を変えるだけで恩恵を受けられることも多いです。

## Zed — ネイティブな共同編集エディタ

[Zed](https://zed.dev/) はRust製のコードエディタです。GPUを活用した描画で軽快に動き、共同編集やAI支援を前提とした設計が特徴です。

VS Codeと比べると拡張機能のエコシステムはまだ発展途上ですが、「起動と入力のレスポンスを最優先したい」という用途では有力な選択肢になります。

## 導入時の現実的なポイント

高速なツールは魅力的ですが、乗り換えにはいくつか注意点があります。

### 1. 互換性を確認する

リンタやフォーマッタは、既存のルールセットと完全に一致しないことがあります。まずはCIで差分を確認し、影響範囲を把握してから本番適用するのが安全です。

### 2. 段階的に移行する

いきなりすべて置き換えるのではなく、フォーマットだけ、lintだけ、と範囲を区切って移行するとトラブルが少なくなります。

### 3. ロックファイルをコミットする

`uv.lock` や `bun.lock` などのロックファイルをリポジトリに含めることで、チーム全員とCIで同じ依存を再現できます。

### 4. チームの合意を取る

ツールチェーンの変更は開発フロー全体に影響します。設定ファイルの場所やコマンドをドキュメント化し、READMEやCONTRIBUTINGに反映しておきましょう。

## まとめ

Rust製ツールの広がりは、単なる「速いツールの流行」ではなく、開発ワークフローの再設計につながっています。

- **uv / Ruff** でPythonの依存管理とlintを高速化する
- **Biome** でJS/TSのツールチェーンを統合する
- **Bun** でランタイムとツールをまとめる
- **Zed** で編集環境をネイティブに寄せる

すべてを一度に導入する必要はありません。まずは1つ、日常的に待ち時間が発生している箇所から試してみるのがおすすめです。小さな改善の積み重ねが、結果的に開発体験を大きく変えてくれます。
