開発ツールの進化は年々速くなり、何をキャッチアップすべきか迷う場面も増えました。本記事では、最近のプログラミング界隈で関心が高いテーマを整理し、実務でどう向き合うかを紹介します。個別のバージョンや仕様は変化が早いため、導入時は必ず公式ドキュメントを確認してください。

## AIコーディングは「補完」から「委任」へ

ここ1〜2年で、AIコーディングの重心はエディタ上の入力補完から、タスク単位の実装を任せるスタイルへ移ってきました。エージェントにIssueを渡し、テストを書き、Pull Requestまで作らせるワークフローを組むチームも増えています。

うまく運用するには、任せる範囲を小さく保つことが重要です。

- 1つのPRを小さくし、レビュー可能な差分に収める
- テストと静的解析をCIで必ず通す
- 生成物であることを前提に、設計意図を人間が確認する
- シークレットや社外秘の情報をプロンプトへ含めない

「AIが書いたから正しい」ではなく、「検証可能な形で出力させる」という設計が定着の鍵になります。

## MCPでツール連携を標準化する

MCP（Model Context Protocol）は、LLMと外部ツールやデータソースをつなぐための仕組みです。エージェントごとに独自の連携コードを書く代わりに、共通のインターフェースでリポジトリやデータベースへアクセスできます。

設定はJSONで記述する形が一般的です。

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./"]
    }
  }
}
```

便利な反面、エージェントに渡す権限は最小限に抑える必要があります。読み取り専用のツールから始め、書き込みや外部通信が必要になった段階で範囲を広げるのが安全です。

## TypeScriptコンパイラのネイティブ化と高速化

TypeScriptのツールチェーンでは、コンパイラをネイティブ言語で実装し直す取り組みが話題になっています。型チェックやエディタの応答が高速になれば、大規模プロジェクトでの待ち時間は大きく変わります。

一方で、移行期には既存の挙動と差異が出る可能性があります。導入を検討する際は、次の点を確認しましょう。

- 使用している周辺ツール（Lint、バンドラ、エディタ拡張）の対応状況
- 型の推論やエラーメッセージの差分
- CIの実行時間とキャッシュ戦略への影響

速度の恩恵は大きいですが、まずはサブプロジェクトで検証するのが現実的です。

## Rust製ツールが開発者体験を変える

Lint、Formatter、パッケージ管理、エディタなど、Rustで実装されたツールが存在感を増しています。単一バイナリで配布され、起動が速く、設定も比較的シンプルなものが多いのが特徴です。

たとえばJavaScript/TypeScriptではBiome、PythonではRuffやuv、エディタではZedがよく話題に上がります。コマンド例は次のとおりです。

```bash
biome check --write .
uv add requests
uv run python main.py
```

既存の設定を一気に置き換えるのではなく、まずはFormatだけ、次にLintといった形で段階的に導入すると差分を追いやすくなります。

## ローカルLLMという選択肢

コードや文章を外部サービスへ送れない場面では、ローカルで動くLLMが有力です。Ollamaのようなツールを使えば、モデルを取得してすぐに試せます。

```bash
ollama run llama3
```

OpenAI互換のAPIを備えるものもあり、既存ツールから接続しやすいのが利点です。ただし、モデルサイズに応じてメモリやGPU性能が必要になるため、まずは小さめのモデルで用途を確かめるとよいでしょう。

## 導入を進めるためのチェックリスト

- ロックファイルをリポジトリへコミットする
- ローカルとCIで同じツールバージョンを使う
- ライセンスとセキュリティポリシーを確認する
- チーム内で設定ファイルの管理ルールを決める
- 小さく試し、効果を測ってから展開する

## まとめ

AIエージェント、MCP、ネイティブ化するコンパイラ、Rust製ツール、ローカルLLM。どれも「開発の待ち時間を減らし、本質的な作業に集中する」方向へ向かっています。
