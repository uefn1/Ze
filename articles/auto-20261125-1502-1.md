## はじめに — 「ツールの速度」が開発体験を決める時代

ここ数年で、開発ツールの世界は静かに、しかし確実に塗り替えられています。キーワードは**ネイティブ実装**です。PythonやJavaScriptで書かれていた定番ツールが、RustやZig、Goで書き直され、桁違いの速度を手に入れています。

本記事では、2026年現在の実務で「もう戻れない」と感じるツール群を、実際のコマンドと移行手順つきで紹介します。対象は以下です。

- **uv** — Pythonのパッケージ・プロジェクト管理
- **Ruff** — PythonのLint/Format
- **Biome** — JavaScript/TypeScriptのLint/Format
- **Bun** — JavaScriptランタイム兼ツールチェーン

いずれも「速い」だけでなく、設定ファイルの一本化やロックファイルの扱いなど、**運用面でのメリット**が大きいのが特徴です。

## なぜネイティブ実装が強いのか

理由はシンプルです。

1. **起動が速い** — スクリプト言語のランタイム起動コストがない
2. **並列化しやすい** — Rust/ZigはスレッドやI/Oの扱いを細かく制御できる
3. **依存が少ない** — 単一バイナリで配布でき、CIでのセットアップが軽い

特にCIでは、Lintやテストの前段にある「インストール」「フォーマットチェック」の時間が積み上がります。ここが数秒から数十秒単位で縮むと、PRのフィードバックループが体感で変わります。

## uv — Python環境構築を「一瞬」にする

### uvとは

uvはAstral社が開発する、Rust製のPythonパッケージ・プロジェクトマネージャです。pip、pip-tools、virtualenv、pyenv、poetryの役割を**ひとつに統合**することを狙っています。

### インストール

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Homebrew
brew install uv
```

### プロジェクトを始める

```bash
uv init myapp
cd myapp
uv add requests
uv run python main.py
```

`uv init` で `pyproject.toml` と `.python-version` が生成され、`uv add` は依存追加とロックファイル（`uv.lock`）更新を同時に行います。仮想環境の有効化（`source .venv/bin/activate`）は**不要**です。`uv run` が適切な環境でコマンドを実行してくれます。

### 既存プロジェクトへの導入

```bash
# requirements.txt から移行
uv init
uv add -r requirements.txt
```

`uv pip install` はpip互換なので、既存のCIを壊さず段階的に移行できます。

```bash
# 従来の使い方もそのまま
uv pip install -r requirements.txt
uv pip sync requirements.txt
```

### 速度の目安

体感ですが、数十個の依存を持つプロジェクトのクリーンインストールが、pip+venvでは数十秒かかっていたところ、uvでは数秒で終わることが多いです。CIのキャッシュと組み合わせると効果はさらに大きくなります。

## Ruff — LintとFormatを1ツールに

### Ruffとは

RuffもAstral製のRustツールで、flake8・isort・pyupgrade・black（フォーマッタ）などの役割を置き換えます。設定は `pyproject.toml` に集約できます。

### 導入

```bash
uv add --dev ruff
```

### 設定例

```toml
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
ignore = ["E501"]

[tool.ruff.format]
quote-style = "double"
```

### 実行

```bash
uv run ruff check .
uv run ruff format .
uv run ruff check --fix .
```

`ruff check` がLint、`ruff format` がフォーマットです。`--fix` で自動修正できるルールも多く、レビュー前に機械的な指摘を潰せます。

### 移行のコツ

既存プロジェクトでは、いきなり `select = ["ALL"]` にすると大量の警告が出ます。まずは `E`, `F`, `I` など基本ルールから始め、CIが緑になってから段階的に追加するのが現実的です。

## Biome — JS/TSのLintとFormatを統合

### Biomeとは

BiomeはRust製のJavaScript/TypeScriptツールチェーンで、PrettierとESLintの役割をまとめて担います。設定は `biome.json` に一本化されます。

### 導入

```bash
npm install --save-dev --save-exact @biomejs/biome
npx biome init
```

### 設定例

```json
{
  "$schema": "https://biomejs.dev/schemas/1.9.0/schema.json",
  "formatter": {
    "enabled": true,
    "indentStyle": "space",
    "lineWidth": 100
  },
  "linter": {
    "enabled": true,
    "rules": {
      "recommended": true
    }
  }
}
```

### 実行

```bash
npx biome check .
npx biome check --write .
npx biome format --write .
npx biome lint .
```

`biome check` はLint・Format・import整理をまとめて実行します。CIでは `biome check .` を、ローカルでは `--write` 付きで使う、という運用が定番です。

### ESLint/Prettierからの移行

```bash
npx @biomejs/biome migrate eslint --write
npx @biomejs/biome migrate prettier --write
```

移行コマンドが用意されているため、既存設定の多くを自動で変換できます。ただしESLintのプラグインすべてが同等にサポートされるわけではないので、移行後にルール差分を確認しましょう。

## Bun — ランタイムもツールチェーンも速く

### Bunとは

BunはZig製のJavaScriptランタイムで、パッケージマネージャ・バンドラ・テストランナーを内蔵しています。Node.js互換を意識しつつ、起動とインストールが高速なのが売りです。

### 導入と実行

```bash
curl -fsSL https://bun.sh/install | bash

bun init
bun add hono
bun run index.ts
bun test
```

TypeScriptをトランスパイルなしで直接実行できるため、ちょっとしたスクリプトやCLIの試作が快適です。

### パッケージインストール

```bash
bun install
```

`bun.lockb`（バイナリロックファイル）を使い、`npm install` より高速に完了することが多いです。CIでは `bun install --frozen-lockfile` で再現性を担保します。

### 注意点

- Node.jsのネイティブアドオンなど、一部エコシステムとの互換性に制約がある場合があります
- 本番採用時は、利用ライブラリがBunで動作するかを事前に検証しましょう

「まず開発体験としてBun、互換性が問題になる箇所だけNode.js」という使い分けも現実的です。

## 実務での組み合わせ方

言語ごとに、次のような構成が扱いやすいです。

| 領域 | ツール | 役割 |
| --- | --- | --- |
| Python 環境 | uv | 依存管理・仮想環境・Pythonバージョン |
| Python Lint/Format | Ruff | flake8/isort/black の置き換え |
| JS/TS Lint/Format | Biome | ESLint/Prettier の置き換え |
| JS/TS 実行 | Bun | ランタイム・テスト・バンドル |

ポイントは**設定ファイルを減らす**ことです。Pythonは `pyproject.toml`、JS/TSは `biome.json` に寄せると、新規参加者のキャッチアップが楽になります。

## CIへの組み込み例

GitHub Actionsでの最小構成はこんな形です。

```yaml
name: ci
on: [push, pull_request]

jobs:
  python:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv sync --frozen
      - run: uv run ruff check .
      - run: uv run ruff format --check .
      - run: uv run pytest

  web:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install --frozen-lockfile
      - run: bunx biome check .
      - run: bun test
```

`--frozen` / `--frozen-lockfile` を付けることで、ロックファイルと差分があれば失敗させ、CIとローカルの環境差異を防げます。

## まとめ

2026年の開発ツールは、**「速い」が前提**になりつつあります。uvとRuffでPythonを、BiomeとBunでJS/TSを整えると、日常の待ち時間が減るだけでなく、設定の見通しも良くなります。

まずは1つだけ試すなら、Pythonなら**uv**、JS/TSなら**Biome**が導入コストと効果のバランスが良いと思います。小さく始めて、CIが緑のまま少しずつ置き換えていきましょう。
