コードを書く主語が「自分」から「自分とエージェント」に変わりつつあります。補完だけだったAIは、リポジトリを読み、コマンドを実行し、差分を作る存在になりました。本記事では、そんな変化に合わせて2026年に見直しておきたい開発ツールと、その使い方を整理します。

## ツール選びの基準が変わった

これまでは「人がどれだけ快適に書けるか」が中心でした。現在はそこに、次の観点が加わります。

- エージェントが文脈を取得しやすい構造になっているか
- 同じ設定をローカルとCIで再現できるか
- 危険な操作を権限で制御できるか
- フィードバックが速く、修正ループを回せるか

派手な新機能よりも、この4点を満たす地味なツールが効いてきます。

## 1. MCPでエージェントに文脈を渡す

MCP（Model Context Protocol）は、エージェントと外部ツール・データをつなぐための共通規格です。ファイルシステム、データベース、社内APIなどを、エージェントごとに個別実装せず接続できます。

設定はクライアント側のJSONにまとめるのが一般的です。

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./"]
    }
  }
}
```

重要なのは、渡す範囲を絞ることです。リポジトリ全体ではなく必要なディレクトリだけを公開し、読み取り専用のサーバーから始めると事故を減らせます。MCPは便利さと引き換えに権限が広がるため、「何を読ませるか」を設計対象として扱いましょう。

## 2. エージェントCLIは再現できる設定で使う

ターミナルから動くエージェントCLIは、レビューや調査のような単発作業と相性が良いです。

```bash
opencode run "このリポジトリで失敗しているテストを調査して"
```

便利な一方で、設定が個人の環境に閉じるとチームで再現できません。使用するモデル、許可するコマンド、参照するMCPサーバーをリポジトリ内の設定ファイルに寄せ、レビュー対象に含めるのがおすすめです。

また、エージェントの出力は必ず差分として確認します。説明がもっともらしくても、テストが通るとは限りません。「生成させる」ではなく「検証させる」意識が大切です。

## 3. フィードバックを速くするLintとFormat

エージェントは人間より多くの差分を短時間で出します。だからこそ、LintとFormatの速度が開発体験を大きく左右します。

```bash
npx @biomejs/biome check --write .
```

BiomeのようにLintとFormatを1つの設定で扱えるツールは、エージェント向けの指示もシンプルになります。「保存時に整形、CIで検査」という同じルールを、人とエージェントの双方に適用できるからです。

ルールを増やしすぎると修正ループが長くなるため、まずはエラーになるルールを最小限にし、慣れてから段階的に強めていくと定着します。

## 4. 依存と実行環境の再現性を守る

エージェントが環境を変更する場面では、ロックファイルとバージョン固定が防波堤になります。Pythonならuvのように、依存解決・仮想環境・ロックを一貫して扱えるツールが扱いやすいです。

```bash
uv sync --locked
uv run pytest
```

`--locked`を付けておけば、ロックファイルと異なる解決が必要になった時点で失敗します。CIでも同じコマンドを使えば、「ローカルでは動いた」を減らせます。

JavaScript/TypeScript側も、パッケージマネージャを1つに統一し、ロックファイルを必ずコミットする運用が基本です。

## 5. ローカルLLMは機密と速度で使い分ける

すべてをクラウドのモデルに送る必要はありません。社内コードや個人情報を含む処理は、ローカルで動くモデルに向いています。

```bash
ollama run <model>
```

ローカル実行は外部送信を避けられる一方、モデルサイズに応じてメモリやGPUが必要です。用途ごとに次のように分けると判断しやすくなります。

| 用途 | 向いている選択 |
| --- | --- |
| 機密性の高いコードの要約 | ローカルLLM |
| 複雑な設計相談 | クラウドの大規模モデル |
| 定型的な変換・整形 | 小規模モデルやルールベース |

## 導入前に決めておきたいルール

ツールを増やす前に、チームで次を決めておくと運用がぶれません。

- エージェントに許可するコマンドと、禁止する操作
- 参照してよいディレクトリと、触れてはいけないファイル
- 生成された差分を誰がレビューするか
- シークレットを環境変数やシークレットマネージャで管理する
- ツールのバージョンをリポジトリで固定する

特に権限まわりは、「便利だから全部許可」を避け、必要になったら広げる方が安全です。

## まとめ

2026年の開発ツールは、人だけでなくエージェントも使う前提で選ぶと差が出ます。MCPで文脈を絞って渡し、CLIの設定を再現可能にし、Lint/Formatと依存管理でフィードバックを速くする。そしてローカルLLMを機密性に応じて使い分ける。

新しいツールを全部試す必要はありません。まずは1つ導入し、修正ループがどれだけ短くなったかを測ってみてください。
