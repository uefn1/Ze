## はじめに

TypeScriptでの開発は便利になった一方で、リンター、フォーマッター、テストランナー、バンドラーと、管理すべきツールが増えがちです。設定ファイルが増えるほど「本来書きたいコード」に辿り着くまでの時間は長くなります。

この記事では、2026年の今あらためて見直したい「設定を増やしすぎない」TypeScriptツールチェーンを紹介します。特定のバージョンに依存した話ではなく、これから新規プロジェクトを始める人・既存プロジェクトの整理を考えている人向けの考え方として読んでもらえれば幸いです。

## なぜツールチェーンを見直すのか

ツールを増やすこと自体は悪ではありません。ただ、次のような状態になっていないでしょうか。

- ESLintとPrettierの設定が二重管理になっている
- テストランナーとバンドラーで別々のトランスパイラ設定を持っている
- `package.json` のscriptsが何十行にもなっている
- 新メンバーが環境構築でつまずく

最近のツールは「1つで複数の役割を担う」方向に進んでいます。役割を統合できるなら、設定も学習コストも減らせます。

## 1. Bun：パッケージ管理・実行・テストをまとめる

BunはJavaScript/TypeScriptのランタイムであり、パッケージマネージャーであり、テストランナーでもあります。Node.jsからの移行が不要な場面も多く、まずはパッケージマネージャーとして試すのがおすすめです。

```bash
# 依存関係のインストール
bun install

# TypeScriptをそのまま実行
bun run src/index.ts

# テスト
bun test
```

従来は `npm` + `ts-node` + `jest` のように分かれていた役割を、Bunひとつで賄えるケースがあります。特に小規模なCLIツールやAPIサーバーでは、設定ファイルなしで動かせる点が魅力です。

ただし、本番環境の互換性やエコシステムの対応状況はプロジェクトごとに異なります。「開発環境だけBun」「CIはNode.js」といった併用も現実的な選択肢です。

## 2. Biome：LintとFormatを1つのツールに

BiomeはJavaScript/TypeScript向けのリンター兼フォーマッターです。ESLintとPrettierを別々に設定する代わりに、1つの設定ファイルで統一できます。

```json
{
  "$schema": "https://biomejs.dev/schemas/1.9.0/schema.json",
  "formatter": {
    "enabled": true,
    "indentStyle": "space",
    "indentWidth": 2
  },
  "linter": {
    "enabled": true,
    "rules": {
      "recommended": true
    }
  }
}
```

```bash
# チェック
bunx biome check .

# 自動修正
bunx biome check --write .
```

設定がシンプルなので、ルールの取捨選択に悩む時間を減らせます。既存プロジェクトでESLintの独自ルールを多用している場合は、いきなり置き換えるのではなく、まずフォーマッターとして導入するのが安全です。

## 3. Vite：フロントエンドのビルドを高速に

フロントエンドの開発サーバーとビルドにはViteが定番です。開発時は必要なモジュールだけをオンデマンドで変換するため、起動が速く、HMR（ホットリロード）も快適です。

```bash
bun create vite my-app
cd my-app
bun install
bun run dev
```

Viteは設定なしでも動きますが、必要になったときだけ `vite.config.ts` を育てていくスタイルがおすすめです。最初からあらゆるプラグインを入れると、かえって構成が複雑になります。

## 4. Hono：軽量なAPIサーバーの選択肢

APIを少しだけ用意したい、という場面ではHonoが使いやすい選択肢です。小さく、TypeScriptとの相性がよく、さまざまなランタイムで動作します。

```ts
import { Hono } from "hono";

const app = new Hono();

app.get("/", (c) => c.text("Hello, Zenn!"));

export default app;
```

BunやCloudflare Workersなど複数の実行環境に対応しているため、後からデプロイ先を変えたい場合にも柔軟です。フルスタックフレームワークほど多くの機能は要らないが、ルーティングとミドルウェアは欲しい、というバランスに向いています。

## 小さく始める移行ステップ

既存プロジェクトを見直す場合は、一度にすべてを変えないのがコツです。

1. まずフォーマッターだけBiomeに置き換える
2. テストを1ファイルだけBunで動かしてみる
3. CIで両方を並行実行し、差分がないことを確認する
4. 問題がなければscriptsとドキュメントを更新する

「動く状態」を保ちながら少しずつ移行することで、ツール変更が原因のトラブルを切り分けやすくなります。

## 導入時の注意点

- バージョンや対応状況は変化が早いため、必ず公式ドキュメントを確認する
- 本番環境のNode.jsバージョンと開発環境の差異を把握しておく
- チーム内で「どのツールが何を担当するか」をREADMEに明記する
- エディタ拡張やCIのキャッシュ設定も合わせて見直す

ツールは目的ではなく手段です。設定の少なさが開発体験の向上につながるなら、積極的に採用してよいと思います。

## まとめ

- Bunでパッケージ管理・実行・テストをまとめられる
- BiomeでLintとFormatの設定を一本化できる
- ViteとHonoは「必要な分だけ設定を足す」使い方がしやすい
- 移行は小さく始め、CIで差分を確認しながら進める

まずは1つのツールだけ、小さく試してみてください。設定ファイルが1つ減るだけでも、開発のリズムは意外なほど変わります。
