## はじめに

ここ数年で、開発ツールの世界は「インタプリタ言語で書かれた定番ツール」から「ネイティブ実装の高速ツール」へと少しずつ主役を交代しています。

Pythonなら `pip` / `virtualenv` / `pyenv` / `flake8` / `black`、JavaScriptなら `npm` / `ESLint` / `Prettier`。これらは長く標準として使われてきましたが、ここに来て **uv**、**Ruff**、**Biome**、**Bun** といった選択肢が実務で現実的に使える成熟度に達してきました。

この記事では、代表的な4つを取り上げ、何を置き換えるのか、実際にどう使うのか、導入時の注意点は何かを整理します。特定のツールを盲信するのではなく、「自分のプロジェクトのどこに効くか」を判断できる状態を目指します。

## なぜ今「ネイティブ実装」なのか

理由はシンプルで、開発体験のボトルネックが「待ち時間」と「設定の分散」にあるからです。

- 依存解決やlintは、本質的にはI/OとCPU処理が中心で、高速化の余地が大きい
- ツールが増えるほど、設定ファイルとバージョン管理の面倒が増える
- CIの実行時間は、そのまま開発者のフィードバック速度に直結する

ネイティブ実装のツールは、単に速いだけでなく **「1つのツールで複数の役割を担う」** 方向に進んでいるのが特徴です。uvはPythonの依存管理と仮想環境を、Ruffはlintとformatを、Biomeはlintとformatを、Bunはランタイムとパッケージ管理をまとめます。

なお、実装言語は統一されているわけではありません。uv・Ruff・BiomeはRust製、BunはZig製です。「Rust製」というより「ネイティブ実装で高速」というくくりで捉えると誤解が少ないです。

## uv: Pythonの依存管理を一本化する

uvはAstral社が開発するPythonのパッケージ・プロジェクト管理ツールです。`pip`、`pip-tools`、`virtualenv`、`pyenv` あたりの役割を、かなり広くカバーします。

### 導入と基本操作

```bash
# プロジェクト作成
uv init myapp
cd myapp

# 依存追加（pyproject.toml と uv.lock が更新される）
uv add requests
uv add --dev pytest

# 仮想環境を同期して実行
uv sync
uv run python main.py

# Python本体のバージョン管理
uv python install 3.12
uv python pin 3.12
```

`uv run` は仮想環境の有効化を意識せずにコマンドを実行できるのが便利です。`source .venv/bin/activate` を忘れる問題から解放されます。

### ロックファイルとCI

`uv.lock` はクロスプラットフォーム対応のロックファイルで、Git管理に含めるのが基本です。CIでは次のように再現性を確保します。

```bash
uv sync --frozen
uv run pytest
```

`--frozen` を付けるとロックファイルの更新を行わず、書かれた通りの状態で同期します。CIで意図せず依存が変わらないようにするために重要です。

### スクリプトのインライン依存

uvはPEP 723のインライン依存にも対応しています。ちょっとしたスクリプトを配布するときに便利です。

```python
# /// script
# requires-python = ">=3.12"
# dependencies = ["httpx"]
# ///

import httpx

print(httpx.get("https://example.com").status_code)
```

```bash
uv run script.py
```

### ツール実行

`uvx`（`uv tool run` のエイリアス）を使うと、グローバル環境を汚さずにCLIツールを実行できます。

```bash
uvx ruff check .
uvx --from httpie http https://example.com
```

## Ruff: lintとformatを1つにまとめる

RuffもAstral社製の、Rustで書かれたPythonのlinter兼formatterです。flake8、isort、pyupgrade、blackなどの役割をまとめて担えます。

### 設定例

`pyproject.toml` にまとめるのがおすすめです。

```toml
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.ruff.format]
quote-style = "double"
```

### 実行

```bash
ruff check .          # lint
ruff check --fix .    # 自動修正
ruff format .         # フォーマット
ruff format --check . # CI向け（差分があれば失敗）
```

blackから移行する場合、`ruff format` はblackとかなり互換性のある出力を目指していますが、完全一致ではありません。移行時に一度全ファイルへ適用し、差分をレビューするのが安全です。

### 実務でのポイント

- flake8のプラグインすべてがRuffにあるわけではないため、`select` で必要なルールを確認する
- `per-file-ignores` でテストやマイグレーションの例外を設定する
- エディタの保存時実行とCIの両方で同じ設定を使う

```toml
[tool.ruff.lint.per-file-ignores]
"tests/**" = ["S101"]
```

## Biome: JS/TSのlintとformatを統合する

BiomeはRust製で、JavaScript/TypeScript/JSON/CSSなどのlintとformatを担当します。元はRomeプロジェクトの流れを汲むツールです。

### 導入

```bash
npx @biomejs/biome init
```

これで `biome.json` が生成されます。設定例は次の通りです。

```json
{
  "formatter": {
    "indentStyle": "space",
    "indentWidth": 2
  },
  "linter": {
    "enabled": true,
    "rules": {
      "recommended": true
    }
  }
}
```

### 実行

```bash
npx @biomejs/biome check .          # lint + format + import整理
npx @biomejs/biome check --write .  # 自動修正
npx @biomejs/biome format --write . # フォーマットのみ
```

`check` がlint・format・importの整理をまとめて行うため、ESLintとPrettierの2つを並べていた構成を1つに寄せられます。

### 実務でのポイント

- ESLintのプラグインエコシステムに依存している場合、Biomeで代替できないルールがある
- フレームワーク固有のルール（React Hooksなど）は対応状況を確認する
- 既存プロジェクトでは、まずformatだけBiomeに移し、lintは段階的に移行すると衝突が少ない

## Bun: ランタイムとパッケージ管理を兼ねる

BunはJavaScript/TypeScriptのランタイムであり、パッケージマネージャでもあります。実装はZigで、Node.jsとの互換性を意識して作られています。

### 基本操作

```bash
bun init
bun add hono
bun add -d typescript
bun run dev
bun test
bunx create-next-app
```

`bun install` は高速で、ロックファイルはテキスト形式の `bun.lock` です。以前のバイナリ形式から変わっているため、古い記事を参照するときは注意してください。

### Node.jsプロジェクトへの導入

いきなりランタイムごと置き換えるのではなく、まずパッケージマネージャとして試すのが現実的です。

```bash
# package-lock.json がある状態から移行する例
rm -rf node_modules
bun install
```

ただし、ロックファイルが変わるため、チーム開発では移行タイミングをそろえる必要があります。CIのキャッシュ設定も見直しましょう。

### 実務でのポイント

- Node.jsのAPI互換は高いが、ネイティブアドオンや一部のエッジケースでは差異がある
- `bun test` はJest互換を意識しているが、すべてのAPIが同じわけではない
- 本番ランタイムに採用するかは、依存パッケージの対応状況を確認してから判断する

## 導入時の共通注意点

高速ツールは魅力的ですが、移行には落とし穴があります。特に意識したいのは次の点です。

### 1. ロックファイルはレビュー対象

`uv.lock` や `bun.lock` は差分が大きくなりがちです。自動生成物だからと無視せず、依存の追加・更新が意図通りか確認します。

### 2. CIを先に整える

ローカルだけ高速化しても、CIがボトルネックなら効果は限定的です。キャッシュキー、実行コマンド、`--frozen` や `--check` の有無を先に設計します。

### 3. 段階的に移行する

いきなり全ツールを置き換えると、問題が起きたときに原因を切り分けられません。まずformat、次にlint、最後にランタイムや依存管理、という順番が安全です。

### 4. エコシステムの差分を把握する

Ruffのルール、Biomeのプラグイン、BunのNode互換性は、既存ツールと完全に同じではありません。移行前に「今使っているルール・機能が代替できるか」を棚卸しします。

## まとめ

今回紹介した4つは、いずれも「速い」だけでなく、設定や役割を統合して開発体験をシンプルにする方向を向いています。

- **uv**: Pythonの依存管理・仮想環境・Pythonバージョン管理をまとめる
- **Ruff**: Pythonのlintとformatを高速に統合する
- **Biome**: JS/TSのlintとformatを1つの設定に寄せる
- **Bun**: ランタイムとパッケージ管理を兼ね、Node.jsの代替を狙う

すべてを今日から置き換える必要はありません。まずは1つのプロジェクトで、CIの実行時間や設定ファイルの枚数がどう変わるかを測ってみるのがおすすめです。小さく試して効果を確認し、チームに展開する。その順番が、高速ツールを安全に取り入れる近道だと思います。
