ChatGPT以降、開発ツールの主戦場は「コードを書く補助」から「エージェントに作業を任せる基盤」へと移りつつあります。一方で、便利さと引き換えに、権限管理やサプライチェーン、プライバシーの課題も表面化しています。

本記事では、いま注目されている技術トレンドを、すぐに試せる形に落とし込んで整理します。特定の製品の優劣を決めるというより、「自分のチームに必要な部品はどれか」を判断するための材料として読んでもらえれば幸いです。

## 2026年の開発ツールを俯瞰する

ここ最近の変化を大きく分けると、次の4つに集約できます。

- **エージェント前提のワークフロー**: 単発の補完ではなく、リポジトリ全体を読んで複数ファイルを編集する
- **ツール接続の標準化**: MCP（Model Context Protocol）のような共通プロトコルで、モデルと外部ツールをつなぐ
- **ローカル実行の再評価**: 機密コードを外部へ出さずにLLMを使いたいニーズの増加
- **防御側の自動化**: 依存関係の混入やサプライチェーン攻撃を、CIで継続的に検出する

以下、それぞれの実践ポイントを見ていきます。

## 1. エージェント前提のワークフローを設計する

コーディングエージェントは、指示を与えるだけで複数ファイルの変更案を出してくれます。しかし、そのまま本番ブランチへ流すのは危険です。重要なのは「エージェントに何を任せ、どこで人間が確認するか」を決めることです。

おすすめの分担は次のとおりです。

| 作業 | エージェント | 人間 |
| --- | --- | --- |
| 調査・原因の特定 | ◎ | 結果の妥当性確認 |
| 定型的なリファクタリング | ◎ | 差分レビュー |
| テストの追加 | ○ | テスト観点の確認 |
| 設計方針の決定 | △ | ◎ |
| 本番デプロイ | × | ◎ |

エージェントに渡す指示は、毎回チャットで書くよりもリポジトリ内のファイルに置くほうが再現性が上がります。たとえば `AGENTS.md` に、ビルド・テスト・Lintのコマンドと禁止事項をまとめておきます。

```markdown
# AGENTS.md

## セットアップ
- 依存関係のインストール: `pnpm install`
- テスト: `pnpm test`
- Lint: `pnpm lint`

## ルール
- `main` ブランチへ直接コミットしない
- 秘密情報をコードやログに含めない
- 破壊的なマイグレーションは必ず提案として出す
```

地味な内容ですが、このファイルがあるだけでエージェントの暴走をかなり抑えられます。CIと同じコマンドを書いておけば、生成された変更をその場で検証できるのも利点です。

## 2. MCPでツールとモデルを疎結合にする

MCP（Model Context Protocol）は、LLMアプリケーションと外部ツール・データソースをつなぐためのプロトコルです。エディタやエージェントごとに独自の連携コードを書くのではなく、共通のインターフェースでツールを公開できます。

概念としては、次の3つを押さえれば十分です。

- **Tools**: モデルが呼び出せる関数（DB検索、API呼び出しなど）
- **Resources**: モデルが参照するデータ（ファイル、ドキュメントなど）
- **Prompts**: 再利用可能な指示テンプレート

設定はクライアント側のJSONにサーバーを登録する形が一般的です。

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./docs"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```

導入時に気をつけたいのは**権限の最小化**です。ファイルシステムサーバーにリポジトリ全体を渡すと、意図しないファイルまで読み書きされる可能性があります。まずは `docs/` のような限定ディレクトリから始め、必要になったら範囲を広げるのが安全です。

また、MCPサーバーは「モデルが呼ぶ外部プロセス」です。信頼できる提供元か、コードを確認できるかを必ずチェックしてください。便利なサーバーを入れるほど、攻撃面も広がります。

## 3. ローカルLLMを現実的な選択肢として扱う

機密性の高いコードや顧客データを扱う場合、外部APIへ送信できないケースがあります。そこで再注目されているのが、ローカルで動くLLMです。

Ollamaのようなツールを使えば、モデルの取得から実行までをコマンド数個で試せます。

```bash
ollama pull qwen2.5-coder
ollama run qwen2.5-coder "この関数のテストケースを列挙して"
```

ただし、ローカルLLMはクラウドモデルと同等の品質を期待すると肩透かしを食らうことがあります。用途を絞るのがコツです。

- **向いている**: コードの要約、命名の提案、簡単な変換、社内ドキュメントの検索補助
- **向いていない**: 大規模な設計判断、複雑なバグの原因特定、長い文脈をまたぐ推論

ハードウェア要件も無視できません。モデルのサイズに応じてメモリとGPU性能が必要になるため、まずは小さめのモデルで効果を測り、必要なら段階的に上げるのが現実的です。

## 4. サプライチェーン防御をCIに組み込む

AIツールの導入以上に重要になってきているのが、依存関係の安全性です。npmやPyPIなどのエコシステムでは、悪意あるパッケージや乗っ取りが後を絶ちません。

対策は「一度確認する」ではなく「継続的に検出する」ことが前提になります。

- ロックファイルを必ずコミットし、CIで再現性を検証する
- 依存関係の脆弱性スキャンを定期実行する
- SBOM（ソフトウェア部品表）を生成して保管する
- 新しい依存を追加するPRでは、メンテナ状況とライセンスを確認する

GitHub Actionsなら、次のようなステップを追加するだけで最低限の防御になります。

```yaml
name: dependency-check
on:
  pull_request:
  schedule:
    - cron: "0 3 * * 1"

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm audit --audit-level=high
```

`--frozen-lockfile` を付けると、ロックファイルと `package.json` の不整合を検出できます。CIで落とすことで、意図しない依存更新の混入を防げます。

## 5. AIレビューは「補助」として使う

AIによるコードレビューは、定型的な指摘を拾うのに向いています。たとえば、nullチェック漏れ、例外処理の不足、命名の一貫性などです。

ただし、AIレビューだけで承認を完結させるのはおすすめしません。文脈やプロダクトの意図を理解した人間のレビューは依然として必要です。AIには「一次フィルタ」を任せ、人間は設計やトレードオフの確認に時間を使う。この分担が現実的です。

CIに組み込む場合も、最初はコメント投稿のみに留め、ブロッキング条件にはしないほうが運用しやすいでしょう。

## 小さく試すためのチェックリスト

新しいツールをチームへ導入する前に、次の項目を確認してください。

- [ ] 導入する目的を一言で説明できるか
- [ ] 小さなリポジトリや個人環境で試したか
- [ ] 権限・認証情報の範囲を最小化したか
- [ ] 失敗したときに元へ戻せるか
- [ ] ライセンスとセキュリティポリシーに合致するか
- [ ] ローカルとCIで同じバージョンを使えるか

特にAI関連ツールは更新が速く、設定方法も変わります。バージョンを固定し、変更履歴を追える状態にしておくと、突然の破壊的変更に悩まされにくくなります。

## まとめ

今回のトレンドを一言でまとめると、「AIに任せる範囲を広げるほど、境界と検証を明確にする必要がある」ということです。

- エージェントには `AGENTS.md` でルールとコマンドを明示する
- MCPは権限を絞り、信頼できるサーバーだけを使う
- ローカルLLMは用途を限定して現実的に評価する
- サプライチェーン対策はCIで継続的に実行する
- AIレビューは人間の判断を置き換えず、補助に留める

すべてを一度に導入する必要はありません。まずは1つ選び、日々の開発で効果とリスクを測るところから始めてみてください。
