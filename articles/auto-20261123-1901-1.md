## はじめに

新しいツールの話題は尽きません。Rust 製の高速なフォーマッタ、AI 補完、統合ランタイム、次々と登場するパッケージマネージャ……。「とりあえず速いから入れる」という判断は手軽ですが、半年後に「なぜこれを入れているのか」を説明できなくなります。

この記事では、個別のベンチマーク勝負ではなく、**ツールを選ぶときの判断軸**と、その軸で今あらためて見直す価値があるツール群を整理します。特定バージョンの機能ではなく、「どの基準で採用するか」に焦点を当てます。ツールの仕様は変化が速いので、実際の導入時は必ず公式ドキュメントを確認してください。

## 選定の軸を先に決める

ツール比較で最初に見がちなのは速度です。もちろん重要ですが、単独では判断できません。私が最低限見るのは次の5点です。

| 軸 | 問いかけ |
| --- | --- |
| 再現性 | 別のマシン・CI でも同じ結果になるか |
| 単一責任 | 設定ファイルが1つに収まるか、責務が重複しないか |
| 可逆性 | やめるときに半日で戻せるか |
| 失敗時の挙動 | エラーが読めるか、CI で止まるか |
| エコシステム | エディタ・CI・既存ツールと繋がるか |

速度は「同じ土俵のツール同士の最後の一押し」に使うのが健全です。まず再現性と可逆性で絞り、そのうえで速さを比べる。

## 1. パッケージ管理は「速さ」より「再現性」で選ぶ

Python 界隈で近年存在感を増しているのが **uv** です。`pyproject.toml` を軸に、仮想環境・依存解決・ロックファイル（`uv.lock`）をまとめて扱えます。

```bash
uv init myapp
uv add requests
uv sync --frozen
uv run pytest
```

注目すべきはコマンドの速さそのものより、**ロックファイルと `--frozen` による再現性**です。CI では「解決はするが更新はしない」を明示できるため、ローカルと CI のズレが減ります。

JavaScript/TypeScript 側では **pnpm** の `lockfile` 固定や、**Bun** のオールインワン志向が選択肢になります。ここで大事なのは「どのツールが速いか」ではなく、**ロックファイルがリポジトリにコミットされ、CI がそれを尊重しているか**です。

チェックリストとしては、次の3つが満たせていれば十分なことが多いです。

- ロックファイルがバージョン管理されている
- CI で「ロックを書き換えない」モードがある
- 依存の更新が Renovate / Dependabot などで自動化されている

## 2. Lint と Format は1ツールに寄せる

設定ファイルが増えるほど、ルールの衝突とメンテナンスコストが増えます。そこで近年よく選ばれるのが、Lint と Format を1つで担うツールです。

- Python: **Ruff**（Lint + Format）
- JavaScript/TypeScript: **Biome**（Lint + Format）

```jsonc
// biome.json（最小構成のイメージ）
{
  "formatter": { "enabled": true, "indentStyle": "space" },
  "linter": { "enabled": true, "rules": { "recommended": true } }
}
```

```bash
biome check --write .
```

`biome check` のように「検査と修正」を1コマンドにできると、エディタ保存時・pre-commit・CI の3か所で同じ処理を呼べます。**同じ処理を同じコマンドで呼べること**が、実は速度以上に効きます。

移行時は一気に全ルールを有効化せず、`recommended` から始めて段階的に厳しくするのが安全です。フォーマッタの差分が大量に出るとレビューが破綻するため、「フォーマットのみのコミット」を先に作るのが定石です。

## 3. ランタイムとバージョン管理は「宣言」する

「私の環境では動く」を減らす最も簡単な方法は、**バージョンを宣言し、ツールに強制させる**ことです。

**mise** は複数言語のバージョン管理とタスクランナーを兼ねます。`.mise.toml` に必要なバージョンを書き、`mise install` で揃えます。

```toml
[tools]
node = "22"
python = "3.12"

[tasks.test]
run = "pytest -q"
```

```bash
mise install
mise run test
```

ランタイム側では **Bun** や **Deno** のように、実行・テスト・ビルドをまとめて提供するものも定着してきました。選ぶ際は「全部入りだから便利」ではなく、**チームが既に使っているエコシステムと噛み合うか**で判断します。Node.js との互換性が要件なら、移行コストを過小評価しないことです。

## 4. CI は「ピン留め」と「再利用」で守る

GitHub Actions は便利ですが、サプライチェーンの観点で注意が必要です。サードパーティ Action は**タグではなくコミット SHA でピン留め**するのが基本です。

```yaml
- uses: actions/checkout@<commit-sha>
```

また、同じ手順を各ワークフローにコピペすると、修正が漏れます。**再利用可能ワークフロー**（`workflow_call`）や composite action に切り出し、テスト・Lint・ビルドの手順を1か所にまとめると、CI の変更が一貫します。

権限も最小化します。ワークフロー冒頭で `permissions: contents: read` のように明示し、必要なジョブだけ書き込み権限を付ける。地味ですが、被害範囲を狭める効果は大きいです。

## 5. AI 支援は「レビュー可能な形」で使う

AI コーディング支援は日常になりましたが、導入の成否を分けるのはモデルの性能より**出力の扱い方**です。

- 生成コードは必ず差分としてレビューする
- テストを先に用意し、AI にはテストを壊さない前提で書かせる
- コミットは小さく分け、生成物と手修正を混ぜない
- 秘密情報や社内固有のデータをプロンプトに含めない

特に「AI が書いたから速い」ではなく、**レビューとテストで品質を担保できる範囲でのみ速い**という認識が重要です。CI に型チェックとテストが揃っているチームほど、AI 支援の恩恵を安全に受けられます。

## 6. 観測性は最初から「標準」で入れる

アプリケーションの計装は後付けになりがちですが、**OpenTelemetry** を標準として採用しておくと、ベンダー依存を抑えつつトレース・メトリクス・ログを揃えられます。最初から全機能を入れる必要はありません。まずはリクエストのトレースだけ、次に主要メトリクス、という順で広げるのが現実的です。

## 導入の順番

いきなり全部を入れ替えると、問題が起きたときに原因を切り分けられません。おすすめは次の順序です。

1. **バージョン宣言**（mise など）で環境差を潰す
2. **ロックファイル + CI の固定モード**で再現性を確保
3. **Lint/Format の一本化**で差分ノイズを減らす
4. **CI のピン留めと再利用**で安全性と保守性を上げる
5. **AI 支援と観測性**を、テストとトレースを土台に足す

各ステップは独立して巻き戻せるようにしておくと安心です。設定ファイルと CI を別コミットに分けておけば、「合わなければ戻す」が簡単になります。

## まとめ

ツール選びで迷ったら、速度の前に**再現性・可逆性・単一責任**を確認する。これだけで、半年後の自分とチームが助かります。

- パッケージ管理はロックファイルと固定モードで選ぶ
- Lint/Format は1ツールに寄せ、同じコマンドを3か所で使う
- バージョンは宣言して強制する
- CI は SHA ピン留めと再利用で守る
- AI 支援はレビューとテストを前提に使う
- 観測性は標準仕様から小さく始める

新しいツールを追うこと自体は悪くありません。ただ、**「なぜそれを選んだか」を一言で説明できる状態**を保つことが、長く速く開発するコツだと思います。
