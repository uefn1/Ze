## はじめに

「新しいツールを追うのが疲れる」——そう感じる一方で、開発体験を大きく変えるツールが定期的に登場しています。本記事では、2026年時点で実務投入しやすい5つのツールを取り上げ、**何が嬉しいのか / どこでハマるのか**をコード例つきで整理します。

対象読者は、Python・TypeScriptを日常的に書き、CIやローカル環境の高速化に関心があるエンジニアです。

## 1. uv — Pythonの依存管理を「待たない」体験に

Pythonの依存解決は長らく `pip` + `venv` + 各種設定ファイルの組み合わせが煩雑でした。`uv` はRust製のパッケージマネージャで、**インストール・解決・ロックが桁違いに速い**のが特徴です。

```bash
# プロジェクト初期化
uv init myapp
cd myapp

# 依存追加（pyproject.toml と uv.lock が更新される）
uv add fastapi uvicorn

# 仮想環境を使った実行
uv run uvicorn main:app --reload
```

### 嬉しいポイント

- `uv run` により「仮想環境をactivateし忘れる」事故が減る
- `uv.lock` による再現性の高いビルド
- Python本体のバージョン管理も `uv python install 3.13` で完結

### ハマりどころ

- 既存プロジェクトの `requirements.txt` 運用と混在すると、どちらが正になるか曖昧になりがち
- 社内ミラーやプライベートインデックスを使う場合は `[[tool.uv.index]]` の設定を先に確認する

移行時は「新規プロジェクトからuv、既存は段階移行」が現実的です。

## 2. Biome — Lintとフォーマットを1本化する

ESLint + Prettierの二重管理は、設定ファイルの増殖とルール競合の温床でした。Biomeは**リンタとフォーマッタを単一バイナリで提供**し、設定も1ファイルで済みます。

```json
{
  "$schema": "https://biomejs.dev/schemas/1.9.0/schema.json",
  "formatter": {
    "enabled": true,
    "indentStyle": "space",
    "indentWidth": 2
  },
  "linter": {
    "enabled": true,
    "rules": { "recommended": true }
  }
}
```

```bash
biome check --write .
```

### 嬉しいポイント

- 起動が速く、エディタの保存時フォーマットでもストレスがない
- `biome check --write` で lint 修正と整形を一括実行
- 設定の重複がなく、チームでの合意形成が簡単

### ハマりどころ

- ESLintのプラグインエコシステム全部を再現できるわけではない。TypeScriptの型情報を使うルールや独自プラグインに依存している場合は、移行前に棚卸しが必要
- フレームワーク固有のルール（React Hooksなど）は対応状況をバージョンごとに確認する

## 3. Bun — ランタイムとツールチェーンをまとめて高速化

BunはJavaScript/TypeScriptのランタイムであり、パッケージマネージャ・テストランナ・バンドラを兼ねます。「まずスクリプト実行とテストを速くしたい」という用途で効果を発揮します。

```ts
// sum.test.ts
import { expect, test } from "bun:test";

test("加算", () => {
  expect(1 + 2).toBe(3);
});
```

```bash
bun test
bun install
bun run dev
```

### 嬉しいポイント

- TypeScriptをトランスパイルなしで直接実行できる
- `bun test` が高速で、Jest互換のAPIが多く移行しやすい
- `bun install` の速度はCI時間の短縮に直結する

### ハマりどころ

- Node.js固有の挙動やネイティブモジュールに依存する処理は、互換性の確認が必要
- 本番運用ではNode.jsとの差分をテストで担保しておくのが安全

「開発とテストはBun、本番はNode」というハイブリッドも現実的な選択肢です。

## 4. Zed — 共同編集を前提にした高速エディタ

ZedはRust製のエディタで、**起動と入力のレイテンシが小さい**ことに加え、マルチプレイヤーでの共同編集を標準機能として備えています。

### 嬉しいポイント

- GPU描画による滑らかな操作感
- 共同編集セッションでペアプロが容易
- AIアシスタント連携がエディタに統合されている

### ハマりどころ

- 拡張機能の数はVS Codeに及ばないため、利用中の言語・ツールの対応状況を事前確認
- チーム標準を乗り換える場合は、設定の共有方法（プロジェクト設定ファイル）を決めておく

## 5. OpenTelemetry — 可観測性の「共通言語」を押さえる

マイクロサービス化やAI機能の組み込みで、ログ・メトリクス・トレースを横断的に扱う必要性が増しています。OpenTelemetry（OTel）は、その計装と転送の標準規格です。

```ts
import { NodeSDK } from "@opentelemetry/sdk-node";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";

const sdk = new NodeSDK({
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
```

### 嬉しいポイント

- ベンダーロックインを避けつつ、バックエンド（各種APM）を差し替えられる
- 自動計装でHTTPやDB呼び出しのトレースを最小工数で取得できる
- 言語をまたいだ一貫したコンテキスト伝播が可能

### ハマりどころ

- サンプリング戦略を決めないと、コストとノイズが膨らむ
- カーディナリティの高い属性（ユーザーIDなど）をそのままラベルにしない

## 導入優先度の目安

| ツール | 効きやすい場面 | 導入コスト |
| --- | --- | --- |
| uv | Pythonの依存管理・CI高速化 | 低 |
| Biome | JS/TSのlint・format統一 | 低〜中 |
| Bun | テスト・スクリプト実行の高速化 | 中 |
| Zed | 編集体験・ペアプロ改善 | 中 |
| OpenTelemetry | 分散システムの可観測性 | 中〜高 |

最初の一歩としては、**uvとBiome**が既存ワークフローへの影響が読みやすく、効果を実感しやすいでしょう。Bunはテストから、Zedは個人の編集環境から、OTelは新規サービスから、と小さく始めるのがおすすめです。

## まとめ

- ツール選定は「速さ」だけでなく、**チームの運用に馴染むか**で判断する
- 移行は新規領域から段階的に。ロールバック可能な状態を保つ
- 標準規格（OTelなど）に寄せておくと、将来の選択肢を残せる

派手な新機能よりも、「待ち時間が減る」「設定が減る」といった地味な改善が、長期的な生産性に効いてきます。まずは1つ、今週の開発フローに組み込んでみてください。
